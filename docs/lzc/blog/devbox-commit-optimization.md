# 从10分钟到30秒：我们如何优化Devbox发版速度

## 背景问题

Devbox 是一个云端开发环境产品。用户在里面写完代码后，可以保存成一个镜像，下次直接从这个镜像启动，省去重复配置环境的时间。

这个"保存成镜像"的操作叫 commit。早期版本中，这个操作比较慢，小改动也需要等待好几分钟。

我们决定针对小改动发版速度慢的问题进行优化。

## 问题定位

这里需要先解释一个概念：Namespace 是容器运行时的隔离机制，不同的 namespace 就像不同的"房间"，里面的资源互不干扰。

最开始设计时，我们在一个独立的 namespace 里执行 commit 操作，不和主 namespace（叫 `k8s.io`）混在一起。这样做的好处是避免主 namespace 的垃圾回收机制干扰 commit 过程。

但这个设计带来了几个实际问题：

- 每次 commit 都要在独立 namespace 里重新拉取镜像配置，浪费时间
- 两个 namespace 管理起来容易出错
- 用户遇到问题时排查困难

经过深入分析，我们发现直接用主 namespace 并没有本质问题，之前担心的问题有别的解法。于是我们把这个架构简化了，把 commit 操作统一回到主 namespace 执行。

但改完之后，正常使用已经是正常的，但是在压测时又发现了一个新问题。

## 问题复现

我们模拟真实场景：创建两个开发环境，写入 10GB 数据，然后保存镜像。结果失败了，报错说找不到镜像数据。

在说问题之前，先解释一下 commit 的实现方式：为了保证数据一致性，commit 时会先删除 devbox 的旧容器，然后创建一个新容器来执行保存操作。

为什么要这么做？其实有更优雅的方案，比如基于 LVM 快照技术，旧容器继续运行，基于快照创建新容器进行 commit。但实现起来比较复杂，需要处理快照管理和状态同步。相比之下，删除旧容器是最简单粗暴也最可靠的办法，能确保数据不会在 commit 过程中被修改。

排查链路是这样的：

```
容器写入大量数据
    ↓
磁盘使用率升高，触发Kubelet的垃圾回收机制
    ↓
Commit时删除旧容器，准备创建新容器
    ↓
在这个短暂的时间间隙中，基础镜像处于"无主"状态
    ↓
Kubelet扫描发现这个镜像"没人用"，把它删掉了
    ↓
新容器创建时找不到镜像数据，commit失败
```

根本原因就是：旧容器删了，新容器还没建起来，中间这个时间窗口里镜像处于"无主"状态。在磁盘紧张的情况下，Kubelet 会把它当作空闲资源回收掉。

## 解决方案

问题的核心找到了：需要在旧容器删除和新容器创建之间，保护好基础镜像不被回收。

我们用了一个现成的机制：Pin 镜像。在镜像上打个标记，告诉 Kubelet 这个镜像不能删。

关键是要选择合适的时机打标记。如果在上层组件里做，需要轮询镜像状态，有的镜像拉取要十几分钟，这个方案不现实。

最后我们选择在镜像拉取环节就打上标记。这里要说一下，Devbox 用的容器运行时 Containerd 是经过定制的，具体定制了一个自研的存储插件（Snapshotter）。

Snapshotter 负责管理容器的存储层，是容器技术里的核心组件。我们的 Snapshotter 是无侵入设计的，可以独立运行。只要识别出当前使用的是我们的 Snapshotter，就自动把对应的镜像 pin 住。

这样用户感知不到任何变化，但 Kubelet 就知道这些镜像不能删了。

## 实施细节

代码改动不大，主要在镜像拉取时加个判断。但实施过程中有几个细节需要处理。

### 1. 镜像引用的类型

在容器世界里，同一个镜像有三种引用方式：

- **repoTag**：带名字的标签，比如 `nginx:latest`
- **repoDigest**：带摘要的引用，比如 `nginx@sha256:abc...`
- **imageID**：纯摘要，比如 `sha256:abc...`

这三种引用指向的是同一个镜像数据，但在容器存储系统里是三条独立的记录。

### 2. 我们踩过的坑

一开始实现时，我们把这三种引用都 pin 住了。看起来很保险，但带来了问题：

当 commit 完成后，系统会把镜像推送到远程仓库保存（持久化），然后删除本地的临时镜像来节约磁盘空间。这个删除操作只会删掉 repoTag 引用。但 repoDigest 和 imageID 还被 pin 着，垃圾回收删不掉。时间一长，磁盘里堆满了这些删不掉的引用。

### 3. 最终方案

分析后发现，只需要 pin 住 repoTag 就够了。这样既保护了镜像不被删，又不影响正常的清理流程。

修改后，删除镜像时所有引用都能正常清理，磁盘占用恢复正常。

### 4. 存量实例迁移

代码改完了，但线上已经有很多运行中的实例，它们的镜像还没有 pin 标记。直接上线的话，这些实例 commit 时还是会出错。

所以我们写了个迁移脚本，扫描当前节点上所有的 Devbox 实例，把它们的 base image 都打上标记。

## 效果

修改后，kubelet 的日志里能看到这样的记录：

```
Image is pinned, skipping garbage collection
```

commit 操作成功率从偶尔失败变成了稳定成功，耗时也从几分钟降到了 30 秒左右。

## 总结

这个优化看起来不大，但涉及了好几个层面的思考：

- **简化架构**：去掉不必要的独立 namespace，降低复杂度
- **理解机制**：搞清楚 Kubelet 的垃圾回收逻辑，找到合适的保护点
- **选择时机**：在镜像拉取时自动打标记，避免异步等待
- **存量迁移**：确保线上实例平滑过渡

最终把Devbox在进行小变更时的发版时间从几分钟降到 30 秒，开发体验明显提升。

## 后续优化方向

当前 commit 时需要删除旧容器，虽然能保证数据一致性，但会造成用户使用中断。我们正在探索基于 LVM 快照的优化方案：旧容器继续运行，基于快照创建新容器进行 commit，用户在 commit 期间可以继续使用开发环境，体验会更流畅。
