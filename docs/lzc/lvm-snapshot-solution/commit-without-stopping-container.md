# Commit 优化方案：基于 LVM 快照实现无中断保存

## 背景

当前 Devbox 的 commit 操作需要先删除旧容器，然后创建新容器来执行保存。这种实现方式虽然简单可靠，但会造成用户使用中断，体验不够流畅。

我们希望探索一种更优雅的方案：**用户在 commit 期间可以继续使用开发环境，无需中断**。

## 当前实现的问题

### 当前的 commit 流程

```
1. 删除 devbox 旧容器
2. 创建新容器
3. 基于新容器执行 commit 操作
4. 完成
```

### 存在的问题

1. **用户体验中断**：删除容器后，用户无法继续工作
2. **时间窗口风险**：删除旧容器到创建新容器之间存在时间间隙，可能触发 Kubelet GC 导致镜像被删
3. **状态丢失**：用户正在进行的操作会中断

### 为什么选择删除容器？

虽然不优雅，但这是最简单粗暴也最可靠的方案：
- 能确保数据不会在 commit 过程中被修改
- 不需要处理复杂的状态同步
- 实现简单，边界情况少

## 技术方案探索

### 方案对比

| 方案 | 优点 | 缺点 | 可行性 |
|------|------|------|--------|
| **删除旧容器（当前）** | 简单可靠 | 用户中断 | ✅ 已实现 |
| **暂停容器** | 数据不变 | 用户体验差，容器卡死 | ⚠️ 可行但体验不好 |
| **只读重新挂载** | 进程不停止 | 可能导致进程崩溃 | ⚠️ 有风险 |
| **断开用户会话** | 不影响容器内进程 | 无法阻止后台写入 | ❌ 不完整 |
| **LVM 快照** | 用户体验最好，无需中断 | 实现复杂 | ✅ 推荐方案 |

### 方案 1：暂停容器

通过 SIGSTOP 信号或 cgroup freezer 暂停容器内所有进程。

**优点**：
- 能确保数据不再变化
- 技术上可行

**缺点**：
- 用户体验差，容器会"卡死"
- commit 完成前用户无法操作
- 可能影响定时任务等后台服务

**结论**：可行但体验不好，不推荐

### 方案 2：只读重新挂载

将容器的根文件系统重新挂载为只读模式。

**优点**：
- 容器内进程不停止
- 技术上可行

**缺点**：
- 容器内进程可能因写入失败而崩溃
- 用户会看到错误提示
- 需要修改挂载点，可能影响稳定性

**结论**：有风险，不推荐

### 方案 3：断开用户会话

断开用户和容器的 PTY 连接或网络连接。

**问题**：
- 只断开了用户的访问入口
- 容器内的进程还在运行，可能后台写入数据
- Shim 负责容器生命周期管理，不控制 I/O 流
- 无法真正阻止数据变化

**结论**：方案不完整，不可行

### 方案 4：LVM 快照（推荐）⭐

利用 LVM 的快照功能，基于逻辑卷的即时快照创建新容器。

#### 工作原理

```
1. 用户容器运行中，继续写入数据
   ↓
2. 对底层逻辑卷创建 LVM 快照（瞬间完成）
   ↓
3. 基于快照创建新容器执行 commit
   ↓
4. 用户容器继续运行，不受影响
   ↓
5. Commit 完成后清理快照
```

#### LVM 快照的特点

- **瞬间完成**：LVM 快照是 Copy-on-Write 机制，创建快照只需要几毫秒
- **空间高效**：只保存变化的数据块，不占用完整副本空间
- **不影响原卷**：原卷可以继续读写，快照保存创建时的数据状态
- **原生支持**：LVM 是内核功能，稳定可靠

#### 优势对比

| 特性 | 删除容器方案 | LVM 快照方案 |
|------|-------------|--------------|
| 用户体验 | ❌ 中断 | ✅ 无中断 |
| 数据一致性 | ✅ 可靠 | ✅ 可靠 |
| 实现复杂度 | ✅ 简单 | ⚠️ 中等 |
| 时间窗口风险 | ⚠️ 存在 | ✅ 无 |

## 实现方案

### 架构设计

```
┌─────────────────────────────────────────────────────────────┐
│                      用户容器（运行中）                        │
│                  基于逻辑卷 /dev/vg/lv001                     │
│                  用户继续写入，不受影响                        │
└─────────────────────────────────────────────────────────────┘
                            │
                            ▼ 创建 LVM 快照
┌─────────────────────────────────────────────────────────────┐
│                   LVM 快照 /dev/vg/lv001-snap                │
│                 保存创建时刻的数据状态                        │
│                 Copy-on-Write，只保存变化                     │
└─────────────────────────────────────────────────────────────┘
                            │
                            ▼ 基于快照创建容器
┌─────────────────────────────────────────────────────────────┐
│                   Commit 容器（临时）                         │
│              基于快照卷，执行 commit 操作                      │
│              和用户容器完全隔离，互不影响                     │
└─────────────────────────────────────────────────────────────┘
```

### 实现步骤

1. **创建 LVM 快照**
   ```bash
   lvcreate -L <size> -s -n <snapshot-name> /dev/<vg>/<lv>
   ```

2. **基于快照创建容器**
   - 使用快照设备作为容器的根文件系统
   - 通过 Snapshotter API 创建临时容器

3. **执行 commit 操作**
   - 基于临时容器生成镜像
   - 推送到远程仓库

4. **清理快照**
   ```bash
   lvremove -f /dev/<vg>/<snapshot-name>
   ```

### 关键技术点

#### 1. 快照大小管理

LVM 快照需要预留空间来保存 Copy-on-Write 的数据块：

```go
// 计算快照大小
// 方式1：固定大小（简单但可能不足）
snapshotSize := "10G"

// 方式2：根据使用情况动态计算
// 监控原卷的变化速度，预留足够空间
```

#### 2. 快照生命周期

```
创建快照 → 基于快照创建容器 → 执行 commit → 清理快照
   ↓            ↓                    ↓             ↓
 瞬间完成      几秒               几十秒        瞬间完成
```

需要确保快照在 commit 期间不被自动清理。

#### 3. 错误处理

- **快照创建失败**：回退到删除容器方案
- **快照空间不足**：监控快照使用率，及时扩容或回退
- **清理失败**：实现幂等清理，避免泄漏

### 伪代码

```go
func (s *Snapshotter) CommitForDevbox(ctx context.Context, containerID string) error {
    // 1. 获取容器对应的逻辑卷
    lv, err := s.getLogicalVolumeForContainer(containerID)
    if err != nil {
        return err
    }

    // 2. 创建 LVM 快照
    snapshotName := fmt.Sprintf("%s-commit-%s", lv.Name, time.Now().Format("20060102150405"))
    snapshotLV, err := s.createLVSnapshot(lv, snapshotName, snapshotSize)
    if err != nil {
        // 快照创建失败，回退到删除容器方案
        return s.commitByRemovingContainer(ctx, containerID)
    }

    // 3. 基于快照创建临时容器
    tempContainerID, err := s.createContainerFromSnapshot(ctx, snapshotLV)
    if err != nil {
        s.cleanupSnapshot(snapshotLV)
        return err
    }
    defer s.cleanupSnapshot(snapshotLV)
    defer s.removeContainer(tempContainerID)

    // 4. 执行 commit
    return s.commitContainer(ctx, tempContainerID)
}
```

## 收益分析

### 用户体验提升

| 场景 | 当前方案 | LVM 快照方案 |
|------|---------|--------------|
| Commit 期间用户操作 | ❌ 无法操作 | ✅ 继续使用 |
| 数据中断 | ❌ 有 | ✅ 无 |
| 等待感知 | ⚠️ 明显 | ✅ 几乎无感知 |

### 技术收益

1. **消除时间窗口风险**：不再存在删除容器到创建容器之间的间隙
2. **更优雅的架构**：充分利用 LVM 快照的原生能力
3. **为未来优化奠定基础**：可以在此基础上实现更多特性，比如：
   - 支持多次并发 commit
   - 实现 commit 队列
   - 支持回滚到历史快照

## 风险与挑战

### 1. 快照空间管理

**风险**：快照空间不足会导致快照失效

**应对**：
- 监控快照使用率
- 设置合理的快照大小
- 实现自动扩容机制

### 2. 实现复杂度

**风险**：需要修改现有的 commit 流程

**应对**：
- 设计清晰的接口
- 实现回退机制
- 充分测试

### 3. 性能影响

**风险**：Copy-on-Write 可能带来轻微性能开销

**应对**：
- LVM 快照的性能影响很小（通常 < 5%）
- 可以通过优化 LVM 配置进一步降低

基于 LVM 快照的 commit 优化方案能够显著提升用户体验，同时保持数据一致性和系统可靠性。虽然实现复杂度较当前方案有所增加，但收益明显，是一个值得投入的优化方向。
